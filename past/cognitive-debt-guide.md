# 🛡️ 认知债务防御指南

> **AI 的终点不是让我们不再理解，而是让我们终于有时间去理解。**
>
> 这份指南阐述了认知债务（Cognitive Debt）的概念，以及我们团队如何系统性地对抗它。

---

## 什么是认知债务？

```
代码库存量 ↑↑↑ (AI 几分钟一个 PR)
团队理解力 ↓↓↓ (没有人有时间读代码)
                    ─────────────────
                    认知债务 = 差距
```

**认知债务** = 代码库存量与团队理解力之间的差距。

就像技术债务让代码越来越难改，认知债务让系统越来越难懂。每一行 AI 生成的代码，如果没有经过人类理解的"编译"，就会在地图上增加一片迷雾。

### 症状

- [ ] PR 合并速度越来越快，但没人能说清最新代码的整体架构
- [ ] 新人 Onboarding 时间从 2 周变成了 2 个月
- [ ] Code Review 只在看"对不对"，没人问"为什么这样设计"
- [ ] 遇到 bug 时，第一反应是问 AI，而不是去看代码
- [ ] 某些模块变成了"无人区"——没有人敢改，因为没有人懂
- [ ] 技术决策的理由已经丢失（"谁写的这段代码？为什么这么写？"）

### 一个具体的例子

**这个项目在改进过程中遇到的真事**:

原始版本的 GAE 实现有一个 bug——在 8 个并行环境下，GAE 跨环境边界计算，导致优势估计错误。这个 bug 存在了很久，因为：

1. 代码"看起来是对的"（Lint 通过）
2. 训练"能跑"（不报错）
3. 但成功率是 0%

修好这个 bug 需要真正的**理解**——不是理解语法，而是理解"为什么 GAE 必须在每个环境内独立计算"。这个理解来自于在脑海中模拟数据流，而不是读代码。

**这就是认知债务的代价: 一个"正确"的 bug 让项目卡了 5000 个 episode。**

## 认知债务的四个层次

| 层次 | 描述 | 例子 |
|------|------|------|
| **L0: 操作层** | 知道怎么跑起来 | `python train.py` |
| **L1: 语法层** | 知道代码在做什么 | "这里在计算 PPO-Clip 损失" |
| **L2: 设计层** | 知道为什么这样设计 | "GAE λ=0.95 是为了平衡偏差和方差" |
| **L3: 系统层** | 知道每个部分如何配合 | "如果改了奖励函数，需要同步调整熵系数" |

**认知债务 = 代码在 L3，而团队在 L0-L1。**

## 四个防御工具

### 1. 🗺️ 知识地图 (`docs/knowledge-map.md`)

**是什么**: 团队共用的系统理解地图。Mermaid 图 + 职责矩阵 + 雾图。

**何时用**:
- 新人 Onboarding: 第一天就打开这张地图
- PR Review: 检查改动是否需要更新地图
- 每周: 团队花 5 分钟确认地图反映最新理解

**核心原则**: 谁改代码，谁更新地图。AI 改的代码，人更新地图。

---

### 2. 📖 PR 知识包 (`.github/pull_request_template.md`)

**是什么**: 每个 PR 不仅要包含代码，还要包含"教材"——背景、问题、心智模型、数据流、边界。

**何时用**:
- 创建 PR 时: 填写模板，作为 PR 描述
- AI 生成代码时: 让 AI 同时生成知识包

**与常规 PR 描述的区别**:

| 常规 PR | 知识包 |
|---------|--------|
| "修改了 reward function" | "将距离奖励从线性改为指数衰减，因为…" |
| "修复了 GAE bug" | "GAE 在并行环境下必须 per-env 计算，因为…" |
| "添加了 xxx 功能" | "这个功能属于 xxx 子系统，数据流是…" |

---

### 3. 🚧 理解门槛 (`docs/understanding-gate.md`)

**是什么**: PR 合并前，Reviewer 必须回答的"理解问题"——不是"代码对不对"，而是"我懂不懂"。

**核心规则**:
- **不是多了一个审批步骤**，而是把"理解"加入审批标准
- **Reviewer 答不上来不是 Reviewer 的问题**，是代码可理解性不够
- **微型 PR 跳过**，大型 PR 需要 Walkthrough

**理解门槛的四层**:
1. 定位理解: "这个改动在系统哪里？"
2. 数据流理解: "数据经过哪些变换？"
3. 边界理解: "这段代码不负责什么？"
4. 故障模式理解: "最可能怎么坏？"

---

### 4. 🕹️ Microworld 训练场 (`microworld/ppo_playground.py`)

**是什么**: 一个独立的、最小化的、交互式的环境，让人可以"玩"代码而不是"读"代码。

**何时用**:
- 新人想理解 PPO 算法: 运行模块 1-4
- 有人想调超参数: 运行模块 5
- Code Review 时遇到看不懂的逻辑: 在 Microworld 里隔离运行

**设计原则**:
- 每次只展示一个概念
- 每一步都解释"正在发生什么"和"为什么"
- 所有中间值可见、可修改

## 团队实践路线图

### 第一周: 建立基线

- [ ] 团队一起审阅 `docs/knowledge-map.md`，讨论雾图是否准确
- [ ] 每人选择一个"雾区"，承诺在未来两周内深入理解
- [ ] 创建第一个 PR 知识包（选一个最近的 PR 做范例）

### 第二周: 养成习惯

- [ ] 所有新 PR 使用知识包模板
- [ ] 至少 50% 的 PR 通过理解门槛审查
- [ ] 运行 Microworld，至少一个模块

### 第三周: 深化

- [ ] 团队周会增加"认知 sync"环节（5分钟，更新地图）
- [ ] 复杂 PR 进行 Walkthrough（15分钟，作者带团队走代码）
- [ ] 知识地图开始显示理解度的提升

### 一个月后: 文化

- [ ] 理解门槛成为 PR 的自然流程
- [ ] 雾图上的红色区域开始减少
- [ ] 新人 Onboarding 时间缩短
- [ ] 团队对 AI 生成代码的审视更加严格

## 与 AI 协作的新范式

### 旧范式: AI 替代理解

```
人提需求 → AI 生成代码 → CI 通过 → 合并
                                  ↑
                              没人理解
```

### 新范式: AI 加速理解

```
人提需求 → AI 生成代码 + 知识包 + 地图更新
              ↓
         人审查理解（不是审查代码）
              ↓
         理解门槛通过？
         ├─ 是 → 合并 + 更新地图
         └─ 否 → AI 生成 Microworld → 人进去玩 → 理解 → 合并
```

### 给 AI 的 Prompt 示例

不只是"帮我写代码"，而是:

```
帮我实现 [功能]。同时生成:
1. 知识包: 背景、问题、心智模型、数据流、边界
2. 地图更新: docs/knowledge-map.md 的 diff
3. 理解自测: 3个我应该在合并前能回答的问题
```

## 反模式

| 反模式 | 为什么危险 |
|--------|-----------|
| "这个模块太简单，不需要文档" | 简单是相对的。今天觉得简单，3个月后可能完全不记得 |
| "AI 生成的代码，让 AI 解释就行" | AI 不可靠。理解代码是团队的责任 |
| "先合并再补文档" | 文档债和认知债一样，几乎永远不会"补" |
| "我是唯一懂这个模块的人" | 单点故障。如果这个人离职/休假, 模块变成无人区 |
| "团队太小，不需要这些流程" | 认知债务在单人中也会积累——6个月前的你也是另一个人 |

## 度量

你可以追踪这些指标来判断认知债务在改善还是在恶化:

| 指标 | 改善信号 | 恶化信号 |
|------|----------|----------|
| **雾图覆盖率** | 绿色区域扩大 | 灰色/红色区域扩大 |
| **PR 理解门槛通过率** | 一次通过率 > 70% | 频繁需要 Walkthrough |
| **新人 Onboarding 时间** | 缩短 | 延长 |
| **跨模块修改的勇气** | 团队成员敢改"别人"的代码 | 只敢改自己写的代码 |
| **决策追溯性** | 能追溯到"为什么这样设计" | "不知道, 代码就是这样写的" |
| **AI 生成代码的占比** | 上升（但都经过理解审查） | 上升（直接合并） |

---

## 最后

认知债务不是 AI 的错。AI 是一个放大器——它放大了我们的生产力，也放大了我们的懒惰。

防御认知债务不需要少用 AI。只需要一个简单的原则:

> **每增加一行代码，就增加一行理解。**
> **每删除一行理解，就删除一行代码。**

代码要合并，认知也要合并。团队共用一张地图，每个人都在上面留下足迹。
