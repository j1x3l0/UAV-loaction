# 🚧 理解门槛（Understanding Gate）

> **合并代码前，团队必须回答这些问题。**
> 这不是代码审查——AI 已经检查过 Lint、测试、正确性了。
> 这是**理解审查**——确认代码进入仓库的同时，理解也进入了团队的大脑。

---

## 快速使用

将以下 checklist 复制到 PR 的 comment 中，Reviewer 在 Approve 前逐项确认。

---

## 通用理解门槛（所有 PR）

```markdown
### 🧠 理解审查（Understanding Review）

**Reviewer**: @name
**日期**: YYYY-MM-DD

#### 第一层：定位理解
- [ ] 我能在一句话内说出这个 PR 要解决什么问题
- [ ] 我能在系统架构图中指出这个改动的位置
- [ ] 我知道这个模块的上下游依赖关系

#### 第二层：数据流理解
- [ ] 我能从输入到输出，逐步描述数据经过的每个变换
- [ ] 我理解每个变换为什么是必要的（而不只是知道它做了什么）
- [ ] 我知道输入数据的隐含假设（什么情况下输入会违反预期）

#### 第三层：边界理解
- [ ] 我知道这段代码**不负责**什么（边界在哪）
- [ ] 我能说出一个"看起来应该在这里，但实际上在别处"的逻辑
- [ ] 我知道如果要在 3 个月后修改这段代码，最安全的切入方式是什么

#### 第四层：故障模式理解
- [ ] 我能说出至少 2 种这段代码会出错的方式
- [ ] 我能描述每种故障的表现（日志、指标会怎么显示）
- [ ] 我知道故障时的恢复路径

#### 确认
- [ ] 我已阅读并理解相关模块的知识地图条目
- [ ] 知识地图是否需要更新？如需要，已提交更新
```

## 领域专用理解门槛

### RL 算法改动（ppo_agent.py, sac_agent.py）

```markdown
### 🧠 RL 算法理解审查

#### 奖励函数理解
- [ ] 我能列出奖励函数的每个组件及其设计意图
- [ ] 我能说明如果去掉某个组件，策略会怎么变化
- [ ] 我理解奖励 scale 对各组件的相对重要性

#### 网络架构理解
- [ ] 我能画出网络的层结构（输入→每层→输出）
- [ ] 我理解为什么选择这个架构（而不是更深/更宽/不同的结构）
- [ ] 我理解初始化方式的选择理由

#### 训练动力学理解
- [ ] 我能解释 loss curve 的预期形状
- [ ] 我知道什么信号表示"训练崩了"（critic loss 飙升、entropy 崩溃等）
- [ ] 我理解 GAE λ 参数在偏差-方差权衡中的作用
```

### 环境改动（drone_env.py）

```markdown
### 🧠 环境理解审查

#### 状态空间理解
- [ ] 我能列出状态向量的每个维度并解释其含义
- [ ] 我理解为什么选择这些特征（而不是其他特征）
- [ ] 我知道哪些维度对策略决策最重要（直觉上）

#### 物理仿真理解
- [ ] 我理解 dt=0.05 的物理含义（每步 50ms）
- [ ] 我理解边界反弹和碰撞检测的数学
- [ ] 我能解释 max_steps=500 的选择理由（500 × 0.05s = 25s 真实时间）

#### 奖励设计理解
- [ ] 我理解为什么使用指数衰减的距离奖励（而不是线性）
- [ ] 我理解障碍物势场惩罚的作用范围
- [ ] 我理解到达奖励中时间效率项的设计意图
```

### 训练基础设施改动（train.py, config.py）

```markdown
### 🧠 训练基础设施理解审查

#### 并行化理解
- [ ] 我理解 SyncVectorEnv 的工作原理（同步 step → 收集所有结果 → 返回）
- [ ] 我理解 rollout_steps=2048 是如何分配的（8 env × 256 steps）
- [ ] 我能解释为什么 GAE 必须 per-environment 计算

#### 超参数理解
- [ ] 我能解释每个关键超参数的作用和调节方向
- [ ] 我理解 minibatch_size=64 与 rollout_steps=2048 的关系
- [ ] 我理解 epochs=10 的选择理由（太少欠拟合，太多过拟合）
```

## 理解门槛的灵活使用

### 微型 PR（修复 typo、调整日志、更新注释）
→ 跳过理解门槛，直接 Approve

### 小型 PR（单个函数修改、参数调整）
→ 完成**第一层 + 第二层**

### 中型 PR（新功能、模块重构）
→ 完成**全部四层**

### 大型 PR（架构变更、新算法）
→ 完成全部四层 **+ 领域专用门槛** + **团队 walkthrough（15 分钟）**

---

## 理解失败的处理

如果 Reviewer 无法通过理解门槛：

1. **不是 Reviewer 的问题**。这说明代码或文档缺乏可理解性。
2. **Author 补充 PR 知识包**中的心智模型、数据流和边界描述
3. **考虑使用 Microworld**（见 `microworld/` 目录）让 Reviewer 亲自运行和探索
4. **团队 Walkthrough**：Author 用 15 分钟带团队走一遍代码

## 反模式（不要这样做）

| 反模式 | 为什么有问题 |
|--------|-------------|
| "我信任作者，直接 Approve" | 信任不能替代理解。6 个月后作者离职，没人懂这段代码。 |
| "代码太简单，不需要理解" | 没有"太简单"的代码。最简单的代码也可能有微妙的边界条件。 |
| "AI 生成的代码，AI 会解释" | AI 不负责维护。你的团队负责。 |
| "Review 太忙，先合并再说" | 认知债务就是这样积累的——每次跳过理解，地图就暗一点。 |
