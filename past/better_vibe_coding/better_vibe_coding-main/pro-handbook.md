# 认知债务防御 — Vibe Coding 工程化方法论

> **Vibe Coding 的终点不是"代码能跑"，而是"团队能懂"。**
>
> 本文档是完整方法论手册（20 分钟深度阅读）。日常操作速查 → [flash-card.md](flash-card.md)

---

# 第一部分：核心理念 🔧 必要项

## 1. 认知债务是什么？

**认知债务 = 代码库存量 − 团队理解力**

AI 协作编程的隐藏成本：代码量快速增长，但理解速度跟不上。测试通过、Lint 清零，但没有人真正懂系统。

## 2. 六层防御体系

| 防御层 | 工具 | 回答的问题 |
|--------|------|-----------|
| 工程规则 | RULES.md / .cursor/rules | "代码长什么样？" |
| 知识地图 | docs/knowledge-map.md | "系统长什么样？" |
| PR 知识包 | PR 模板 + Agent | "这个改动改变了什么？" |
| 理解门槛 | docs/understanding-gate.md | "我懂了吗？" |
| Microworld | microworld/ | "我能亲手玩一遍吗？" |
| 能力边界声明 | Agent 的"能力边界"节 | "Agent 什么时候会出错？" |

## 3. 核心原则

- 约束在前，代码在后。规则后置的成本是前置的 3×。
- 一个 Prompt = 一个模块（≤200 行）。AI 在长上下文中错误率增加 3-5×。
- 每增加一行代码，就增加一行理解。
- Vibe 探索 → Spec 固化 → Agent 执行。不要让 AI 替你做架构决策。
- 知道局限的 Agent 比永远说"能做到"的 Agent 更可信。

# 第二部分：4 层理解模型 🔧 必要项

```
第 1 层：定位 (Location)    — 30 秒内在架构图上指出改动位置
第 2 层：数据流 (Data Flow)  — 脑中跑通数据完整路径
第 3 层：边界 (Boundary)     — 说清楚模块不负责什么
第 4 层：故障 (Failure)      — 预测最可能的故障模式
```

这 4 层模型被 `@understanding-reviewer`、`@understanding-gate`、`@microworld-builder` 共用。Code Review 的终点不是"LGTM"，而是"我懂了"。

# 第三部分：Agent 体系 🔧 必要项

## Agent 全景图（10 个）

### 规划层（写代码之前）

| Agent | 模型 | 一句话 | 核心流程 |
|-------|------|--------|---------|
| `@spec-writer` | sonnet | 模糊想法 → 结构化需求规格 | 目标→用户故事→功能清单(P0/P1)→输入/输出约束→禁止事项→质量门槛→测试场景 |
| `@modular-architect` | sonnet | 大任务拆成 3-5 个独立模块（≤200行） | 阅读知识地图→识别拆分边界→输出模块表→按依赖排序 |
| `@knowledge-map-maintainer` | haiku | 更新项目认知地图 | 检查 6 项：模块职责矩阵→依赖图→数据流→雾图→认知快照→关键概念 |

### 执行层（写代码 + 调试）

| Agent | 模型 | 一句话 | 核心流程 |
|-------|------|--------|---------|
| 主对话 | 继承 | 按模块逐个写代码 | 读 CLAUDE.md → 按模块实现 → 附带知识包 |
| `@fast-debugger` | sonnet | 贴错误 → 定位根因 → 最小修复 | 定位(文件+直接原因+根因)→最小修复(不重构)→同类风险检查→验证 |
| `@microworld-builder` | sonnet | 生成独立交互式教学脚本 | 先出设计文档(5段)→用户确认后写 .py |

### 质量层（交付前必须通过）

| Agent | 模型 | 一句话 | 核心流程 |
|-------|------|--------|---------|
| `@knowledge-pack-generator` | sonnet | 代码改动 → WHY+数据流+边界+风险 | 背景→问题→心智模型→数据流表→边界与职责→风险表→3 个自测题 |
| `@understanding-reviewer` | opus | PR 审查可读性（非正确性） | 4 层检查：定位→数据流→边界→故障；生成 4 层理解问题 |
| `@understanding-gate` | opus | 合并前理解门槛检查 | 4 层逐层判定 PASS/FAIL→最终判定→任一 FAIL 即阻止合并 |
| `@output-reviewer` | opus | AI 输出最终审查 | 5 层逐层检查(完整性/事实/逻辑/边界/格式)→标注不确定→修正清单 |

### 反思层（开发后，反馈到下一轮）

| Agent | 模型 | 一句话 | 核心流程 |
|-------|------|--------|---------|
| `@lesson-capturer` | haiku | 每轮开发 → 提取教训 → 写入教训库 | 读取教训库→分析上下文→归类(模式/反模式/陷阱/洞察)→写入标准化条目 |

## 模型分级策略

| 模型 | 适用任务 | 分配的 Agent |
|------|---------|-------------|
| **haiku** | 机械性维护、格式检查、教训总结 | knowledge-map-maintainer, lesson-capturer |
| **sonnet** | 生成、设计、调试 | spec-writer, modular-architect, knowledge-pack-generator, fast-debugger, microworld-builder |
| **opus** | 深度判断、审查、输出质量把关 | understanding-reviewer, understanding-gate, output-reviewer |

**原则**：Haiku 做机械活（$0.03/次），Sonnet 做生成活，Opus 做判断活。按任务复杂度分配模型，月成本可降 60%。

# 第四部分：能力边界与升级路径 🔧 必要项

## 三层能力边界框架

每个 Agent 在其 Prompt 中声明了 `## 能力边界` 节，包含四个子节：

```
### 我不擅长（本模型级别的固有限制）
### 遇到以下情况建议手动操作
### 遇到以下情况建议升级模型
### 升级路径
```

## 各层级边界基线

### Haiku 层

- **不擅长**：深度推理、创造性设计、模糊需求解释、安全审计、判断模块设计合理性
- **建议手动**：架构决策、不可逆操作确认、安全敏感代码审查
- **建议升级**：需要判断的任务 → sonnet；需要审查的任务 → opus

### Sonnet 层

- **不擅长**：对抗性验证、极端边界条件分析、跨多个不相关领域的综合判断、安全风险发现
- **建议手动**：技术选型（框架/库版本）、破坏性变更确认、生产部署审批
- **建议升级**：需要"故意找茬"的审查 → opus；用 opus 做第二审查者

### Opus 层

- **不擅长**：替代领域专家判断、100% 事实准确性保证、实时/生产环境的具体操作、跨 PR 累积债务评估
- **建议手动**：涉及金钱/合规/安全的最终决策、领域特定知识（医学/法律）、"这个设计会不会导致三个月后重写"
- **建议升级**：→ 换不同 opus instance 做交叉验证（opus 是当前最强推理模型）

### 升级路径

```
haiku → sonnet（需判断）  → opus（需审查/找茬）  → 人类（需决策/担责）
```

# 第五部分：Prompt 设计范式 🔧 必要项

所有 Agent 共享一套模板结构：

```markdown
---
name: agent-name
description: 一句话用途 + 触发条件
tools: Read, Grep, Glob, [Edit/Write/Bash]
model: sonnet | haiku | opus
---

你是 [角色名]。你的唯一职责：[一句话职责]。

## 核心理念（可选）
## 工作流程
## 输出格式
## 规则
## 能力边界
  ### 我不擅长
  ### 遇到以下情况建议手动操作
  ### 遇到以下情况建议升级模型
  ### 升级路径
```

**设计原则**：
- 只读 Agent（审查类）只给 `Read, Grep, Glob` —— 绝不允许修改代码
- 写 Agent 只给完成任务必需的工具
- 角色定位 = 一句话职责，不越界

# 第六部分：实战工作流 📋 可加项

## 完整工作流示例

```
需求模糊 → @spec-writer 生成 Spec
需求 >200行 → @modular-architect 拆分模块

逐模块写代码（主对话，≤200行/模块）
  ├─ 每模块写完 → @knowledge-pack-generator 生成知识包
  ├─ 遇到错误 → @fast-debugger 粘贴错误快速修复
  └─ 复杂逻辑 → @microworld-builder 生成训练场

准备合并
  ├─ @understanding-reviewer 理解审查
  ├─ @understanding-gate 通过/不通过
  └─ 重要输出 → @output-reviewer 5 层终审

合并后
  ├─ @knowledge-map-maintainer 更新认知地图
  └─ @lesson-capturer 总结教训 → 写入教训库 → 反馈到下一轮规划
```

## 有效模式（4 条）

| 模式 | 做法 | 教训 |
|------|------|------|
| 论文三轮递进 | 论文速览 → 代码审查 → 修正文档 | 论文有简化倾向，代码是实现真相 |
| 交叉一致性验证 | 多文件修改后 grep 交叉检查 | 人脑不擅长追踪跨文件一致性 |
| 计划进度分离 | MASTER_PLAN.md（写死）+ PROGRESS.md（活文档） | 计划是蓝图，进度是日志——生命周期不同 |
| 按逻辑序审查 | README→算法→环境→模型→渲染→配置 | 字母序破坏逻辑依赖，5 分钟规划阅读顺序可节省大量时间 |

## 反模式（7 条）

| # | 反模式 | 后果 | 正确做法 |
|---|--------|------|----------|
| 1 | 一次让 Agent 做太多 | 超时/截断/质量下降 | 一个 Prompt = 一个模块（≤200行） |
| 2 | 跳过代码直接信论文 | 分析基于错误假设 | 论文速览 → 代码审查 → 修正文档 |
| 3 | 同时改多个不相关文件 | 上下文污染、不一致 | 一次 Agent 调用只做一类修改 |
| 4 | 未确认就删文件 | 隐藏依赖被破坏 | 先列表确认 → 再删除 |
| 5 | 所有 Agent 都用 Opus | 成本爆炸 | 按任务复杂度分配模型 |
| 6 | Agent 不声明能力边界 | 弱模型遇复杂任务产出低质量 | 检查 Agent 的"能力边界"节，按升级路径切换 |
| 7 | 强模型过度自信 | opus 输出被误认为绝对正确 | opus 输出也需交叉验证 |

## 升级决策详解

### 典型场景

**场景 1**：`@knowledge-map-maintainer` (haiku) 发现模块职责可能越界 → 升级到 `@understanding-reviewer` (opus) 做边界审查

**场景 2**：`@spec-writer` (sonnet) 写完 Spec 需要完整性审查 → 升级到 `@output-reviewer` (opus) 做 5 层终审

**场景 3**：`@understanding-gate` (opus) 判定"不通过"但涉及发布节奏 vs 代码质量权衡 → 人类做最终决策

### 手动接管信号

以下信号出现时应人工介入：
- Agent 输出含 `⚠️ 不确定` 标注
- 同一建议反复出现但无进展
- 涉及不可逆操作（数据删除、破坏性迁移、生产变更）
- 涉及合规/法律/财务影响
- 你对输出感觉"不对劲"但说不上来

## 工具权限最小化原则

- **只读 Agent**：spec-writer, modular-architect, knowledge-pack-generator, understanding-reviewer, understanding-gate, output-reviewer → 只给 `Read, Grep, Glob`
- **写 Agent**：fast-debugger, knowledge-map-maintainer, microworld-builder, lesson-capturer → 只给完成任务必需的工具
- **并行**：spec-writer + modular-architect 可同时启动；knowledge-pack-generator + understanding-reviewer 可同时
- **串行**：Spec 确认 → 模块拆分 → 逐模块写代码 → 理解审查 → 合并

## 成本速查

| Agent | 调用次数 | 单次成本估计 |
|-------|---------|-------------|
| spec-writer | 1 次 | ~$0.15 |
| modular-architect | 0-1 次 | ~$0.10 |
| 主对话 | N 次 | ~$0.50/模块 |
| knowledge-pack-generator | N 次 | ~$0.05/模块 |
| fast-debugger | 按需 | ~$0.08 |
| understanding-reviewer | 1 次 | ~$0.50 |
| understanding-gate | 1 次 | ~$0.50 |
| output-reviewer | 按需 | ~$0.50 |
| knowledge-map-maintainer | 1 次 | ~$0.03 |
| lesson-capturer | 1 次 | ~$0.03 |
| microworld-builder | 按需 | ~$0.30 |
| **典型会话总计** | | **~$2-4** |

对比：全功能 Opus 单 Agent 会话消耗 $5-10+，且无独立审查层和知识包输出。

## 完整技巧清单

| # | 技巧 | 适用场景 |
|---|------|---------|
| 1 | 给 Agent 明确的输出格式要求（表格/JSON/bullet list） | 需要结构化结果 |
| 2 | 先让 Agent 列文件清单再决定读哪些 | 不熟悉的代码库 |
| 3 | 长文档修改后做 grep 交叉验证 | 多文件一致性 |
| 4 | 进度追踪用 checkbox 而非大段文字 | PROGRESS.md |
| 5 | 大任务先做微型实验（<1h）再全量 | 训练任务 |
| 6 | 每个关键设计决策记录 WHY（不只是 WHAT） | 知识包 |
| 7 | 计划文档和进度文档分开维护 | 项目管理 |
| 8 | 一个 Prompt = 一个模块（≤200 行） | 代码生成 |
| 9 | 重要输出先自查再交付 | 所有重要输出 |
| 10 | 不确定的地方标注 ⚠️ 而不是硬编 | 事实核查 |
| 11 | 把审查要求写入 System Prompt 让每次输出自动检查 | 团队规范 |
| 12 | 论文先读摘要→方法→实验→局限 → 再做代码审查 | 论文阅读 |
| 13 | 代码审查按：算法→环境→模型→渲染→配置顺序 | 审查新代码库 |
| 14 | 先确认 Agent 的能力边界再委派任务 | 防止低质量输出 |
| 15 | 遇到 Agent 反复无进展 → 升级模型或手动接管 | 打破僵局 |

# 附录：每个 Agent 的设计详情

> 以下为 10 个 Agent 的完整设计文本，供定制和扩展时参考。

## @spec-writer

```
你是 Spec 编写器。你的职责：把模糊的自然语言需求转化为结构化的、可验证的工程规格。

核心理念：Vibe 用来探索，Spec 用来执行。没有 Spec 的 Vibe Coding = 掷骰子。

工作流程：
  1. 阅读 CLAUDE.md 和 docs/knowledge-map.md
  2. 分析用户的需求描述
  3. 生成结构化规格

Spec 格式：
  ## Spec: [功能名称]
  ### 目标 / 用户故事 / 功能清单(P0/P1) / 输入约束 / 输出约束
  ### 禁止事项 / 质量门槛 / 影响范围 / 依赖 / 测试场景

规则：
  - 只读——不修改代码，只输出 Spec
  - 规格必须量化——没有"做好""优化"这种模糊词
  - 如果需求本身有歧义，主动向用户提出澄清问题

能力边界：
  - 我不擅长：验证需求的商业合理性、对抗性审查、跨系统依赖分析
  - 建议手动：技术选型决策、优先级排序(P0/P1/P2)
  - 建议升级：需"故意找茬式"审查 → opus (@output-reviewer)
  - 升级路径：sonnet → opus → 人类
```

## @modular-architect

```
你是模块化架构师。你的唯一职责：把大需求拆成可独立开发的小模块。

拆分原则：职责单一 / ≤200行 / 接口明确 / 可独立开发 / 可独立测试 / 按依赖排序

输出格式：
  ## 需求拆分方案
  ### 拆分概览（N个模块，M行） / 模块列表 / 每个模块的接口定义 / 开发顺序 / 风险点

规则：
  - 只读——不写代码，只输出拆分方案
  - 如果需求太小（≤200行），直接告诉用户"不需要拆分"
  - 先等用户确认拆分方案，再进行下一步

能力边界：
  - 我不擅长：评估技术选型的长期影响、跨模块性能/安全分析、非技术需求拆分
  - 建议手动：破坏性变更的拆分、涉及第三方服务/API的模块边界
  - 建议升级：需从多个方案中选出最优 → opus (@understanding-reviewer)
  - 升级路径：sonnet → opus → 人类
```

## @knowledge-pack-generator

```
你是知识包生成器。为代码改动生成结构化"知识包"。

知识包格式（8 节）：
  1.背景 / 2.问题(痛点+期望+根因) / 3.心智模型(设计WHY) / 4.数据流表
  / 5.边界与职责 / 6.风险表 / 7.理解自测(3题) / 8.知识地图更新建议

规则：
  - 只读——不修改任何文件
  - 如果找不到 knowledge-map.md，标注"知识地图缺失"
  - 知识包长度：200-500 字

能力边界：
  - 我不擅长：发现隐蔽的安全风险、判断设计决策的长期后果、跨项目知识关联
  - 建议手动：涉及安全敏感信息的知识包、边界判断涉及团队分工
  - 建议升级：需推断隐藏设计意图 → opus (@understanding-reviewer)
  - 升级路径：sonnet → opus → 人类
```

## @knowledge-map-maintainer

```
你是知识地图维护员。保持 docs/knowledge-map.md 与代码同步。

检查清单（6 项）：
  1.模块职责矩阵 / 2.依赖图 / 3.数据流 / 4.雾图(Fog Map)
  / 5.认知快照表 / 6.关键概念速查表

规则：
  - 如果 knowledge-map.md 不存在，生成初始模板
  - 每次改动要具体，不要"可能需要更新"
  - 用 Edit 工具直接更新文件

能力边界：
```

## @output-reviewer

```
你是输出审查员。对即将交付的 AI 输出做最终审查。

5 层检查：
  第1层：完整性——是否回答了所有问题？
  第2层：事实准确性——引用的路径/函数名是否真实？
  第3层：逻辑一致性——结论与推理是否自洽？
  第4层：边界与约束——是否超出需求范围？
  第5层：格式与可用性——代码是否包含必要 import/注释/错误处理？

输出：审查结论 + 每层PASS/ISSUE/FATAL + 修正清单 + 不确定性标注

规则：
  - 只读——审查已有内容，不修改原始输出
  - 不要猜测——不确定的地方必须标注
  - FATAL = 不能交付，ISSUE = 可交付但有改进空间

能力边界：
  - 我不擅长：100%事实保证、替代领域专家、"过度自信"风险
  - 建议手动：涉及领域专业知识、高风险交付、多处FATAL或⚠️不确定时
  - 建议升级：换不同opus instance做交叉验证
  - 升级路径：opus → 人类（再往上只能是人类专家+领域知识）
```
