# 理解门槛清单 — Understanding Gate 模板（认知债务防御 V2 第 4 防御层）

> 作用：合并前最后一步的"我懂了吗"清单。由 `@understanding-gate` Agent 走查，可阻止合并。
> 4 层理解模型：定位 / 数据流 / 边界 / 故障。这是"理解而非正确性"的判断核心抽象。
> PR 合并前必须 4 层全部 PASS，或条件 PASS（标注待澄清项 + 补救计划）。
> 删除所有 `<占位符>` / 示例后投入使用。

## 4 层理解检查

### 第 1 层 — 定位（它在哪里）

- [ ] 我能在 30 秒内说出本改动在架构中的位置
- [ ] 我能指出它直接依赖的上游模块和下游模块
- [ ] 我能在 knowledge-map.md 中找到它的对应行（或确认已新增）

**判定**: PASS / FAIL
**证据**: <文件路径:行号 / 一句话>

### 第 2 层 — 数据流（数据怎么流）

- [ ] 我能在不看代码的情况下用一句话说清 输入 → 变换 → 输出
- [ ] 我能画出本改动内部的数据流（至少手画一条主路径）
- [ ] 异常路径也有数据流说明（错误从哪冒出，被谁捕获）

**判定**: PASS / FAIL
**数据流一句话**: <输入 X → 变换 Y → 输出 Z>

### 第 3 层 — 边界（它做什么 / 不做什么）

- [ ] 我能说出它"明确不负责"的事（不只是"负责"）
- [ ] 它没有越界处理本该属于其他模块的职责
- [ ] 它的接口/签名能体现职责边界（名为实之副）

**判定**: PASS / FAIL
**不负责清单**: <3-5 条>

### 第 4 层 — 故障（它会怎么坏）

- [ ] 我能说出最可能的 1-3 个故障模式和触发条件
- [ ] 我知道故障会在哪里被观测到（日志/指标/告警）
- [ ] 我能说出"如果是 X 输入，行为会是什么"

**判定**: PASS / FAIL
**最可能的故障模式**: <1-3 条>

## 综合判定

- [ ] 第 1 层 PASS
- [ ] 第 2 层 PASS
- [ ] 第 3 层 PASS
- [ ] 第 4 层 PASS

### 结论: [通过 / 条件通过 / 阻止合并]

- **通过**: 4 层全 PASS → 可合并
- **条件通过**: 标注 ≤2 项待澄清，每项有明确补救计划 → 可合并并跟进
- **阻止合并**: 任一层 FAIL 且无补救 → 必须回到写代码/Microworld 阶段
