一、控制策略 (Control Policy) 实现差异分析

1.1 论文原文描述

The control policy, represented by a two-layer perceptron, maps the output of the Kalman filter to control commands for the aircraft.
控制策略是一个两层感知器（MLP），将卡尔曼滤波器的输出映射为飞行器的控制指令。
The policy is trained using on-policy model-free deep RL with Proximal Policy Optimization (PPO).
策略使用基于在策略的无模型深度强化学习和近端策略优化（PPO）进行训练。
The control commands consist of a collective thrust and three body angular rates (roll, pitch, yaw), which is the same control interface used by human pilots.
控制指令包括总推力和三个机体角速度（横滚、俯仰、偏航），与人类飞手使用的控制接口相同。

1.3 关键差异解读

差异一：动作空间与控制接口。Swift 论文的控制指令是总推力 + 三个机体角速度，与真实 FPV 飞手的遥控器接口一致。项目实现使用 3 维连续向量作为推力 x/y/z，这是一个简化模型——真实四旋翼的控制是通过调节四个电机转速来改变推力方向和大小的，而不是直接控制 x/y/z 推力。

差异二：策略输入的来源。Swift 论文的控制策略输入来自感知系统（VIO + 门框检测 + 卡尔曼滤波）融合后的低维状态表征。项目实现使用 14 维向量，包含位置、速度、目标相对位置和障碍物信息。这是因为项目是一个纯仿真环境，不涉及传感器和感知系统。

差异三：激活函数。Swift 论文明确使用 tanh 激活函数。项目实现在第一层使用 ReLU，后续层使用 tanh。这种混合使用在 RL 实践中并不罕见，第一层的 ReLU 有助于特征提取，而 tanh 约束输出范围。

差异四：环境并行度。Swift 论文使用 100 个并行环境在仿真中训练。项目实现使用 8 个并行环境（SyncVectorEnv），数量较少但足以提供稳定的梯度估计。论文总训练交互量为 1x10^8，项目训练 200 轮即达 98% 成功率。

1.4 项目创新点（论文未涉及）

1. 自适应熵系数。项目实现了 AdaptiveEntropyCoeff 类，根据当前策略熵动态调整探索强度。Swift 论文未提及该方法，这是项目的创新改进。

2. 梯度裁剪。项目在训练中使用了 max_grad_norm=0.5 的梯度裁剪，防止梯度爆炸。论文未明确说明是否使用梯度裁剪。

3. GAE per-environment 修复。项目发现并修复了并行环境下 GAE 跨环境边界计算错误的关键 bug，这是论文未讨论的工程实践问题。

二、奖励函数 (Reward Function) 实现差异分析

2.1 论文原文描述

During training, the policy maximizes a reward that combines progress towards the next racing gate with a perception objective that rewards keeping the next gate in the field of view of the camera.
训练中，策略最大化一个奖励，该奖励结合了朝向下一个门框的进度和一个感知目标，该目标奖励保持下一个门框在摄像头视野内。
Seeing the next gate is rewarded because it increases the accuracy of pose estimation.
奖励看到下一个门框是因为这会提高位姿估计的精度。

论文奖励函数的数学表达式：

r(t) = r_prog(t) + r_perc(t) + r_cmd(t) - r_crash(t)

2.3 关键差异解读

差异一：任务差异导致奖励结构不同。Swift 论文的任务是竞速（尽快穿越多个门框），奖励围绕"门框进度"设计。项目的任务是点到点导航（避开障碍物到达目标），奖励围绕"目标距离"设计。这是两个完全不同的任务场景，导致奖励函数结构存在必然差异。

差异二：感知奖励不适用。Swift 论文的 r_perc 组件是专门为机载感知系统设计的——奖励智能体保持下一个门框在摄像头视野内，从而提高位姿估计精度。项目是纯仿真环境，无摄像头和感知系统，因此该组件不适用。

差异三：项目新增了三个奖励组件。项目新增了障碍物势场惩罚（r_obs）、到达奖励（r_goal）和超时惩罚（r_timeout）。这三个组件是根据项目的导航任务特点设计的，Swift 论文的竞速场景不需要它们。

差异四：从稀疏到密集的奖励信号。项目原始版本的奖励函数只有 3 个组件（距离改善量x10、碰撞-20、到达+100），大部分时间步的奖励为 0，信号极度稀疏。改进版本参照 Swift 的密集奖励思想，扩展为 7 个组件，每个时间步都有非零奖励信号。这是成功率从 0% 提升到 98% 的核心原因之一。

3.2 对课题的启示

1. Swift 的密集奖励设计思想是核心参考。从稀疏奖励转向密集奖励是项目成功的关键。Swift 论文中每个时间步都有进度奖励和控制平滑奖励，这个思想应该在课题中继续延伸。

2. 任务差异决定了奖励函数差异。竞速与导航是不同的任务，奖励函数必须围绕任务目标设计。课题中的"复杂环境"意味着需要更多的奖励组件来处理动态障碍物、多目标等场景。

3. PPO + 简洁 MLP 架构已验证可行。项目实现证明，Swift 风格的两层 MLP(128x128) + PPO 架构在三维路径规划中是可行且高效的。无需复杂的 CNN 或 Transformer 架构。

4. Sim-to-Real 是课题下一步的关键方向。当前项目是纯仿真，无感知噪声和动力学偏差。Swift 论文的残差建模方法（高斯过程 + k-NN）是将课题从仿真迁移到现实的重要技术路线。

5. 并行环境下的 GAE 实现需要警惕。项目发现的 GAE 跨环境边界计算错误是一个重要的工程教训，在课题的后续研究中应当避免这类错误。
