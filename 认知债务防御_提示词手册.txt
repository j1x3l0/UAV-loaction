═══════════════════════════════════════════════════════════════════════════
第一部分: 核心理念（写给团队看，也写给 AI 看）
═══════════════════════════════════════════════════════════════════════════

1. 认知债务是什么？

   认知债务 = 代码库存量 与 团队理解力 之间的差距。

   AI 几分钟生成一个 PR，测试、Lint、Review 全部自动通过——
   但这些守卫只回答一个问题：代码对不对。
   没有人在回答：你还懂不懂这个系统。

   代码库存量狂飙 +5000，团队理解力却悄悄掉到 18%。
   地图起雾了，技能一个个 LOCKED，你只剩下一个按钮——APPROVE。

2. 四个防御层

   ┌─────────────┬──────────────────────────┬──────────────────────┐
   │ 防御层       │ 工具                      │ 回答的问题            │
   ├─────────────┼──────────────────────────┼──────────────────────┤
   │ 知识地图     │ docs/knowledge-map.md     │ "系统长什么样？"      │
   │ PR 知识包   │ PR 模板 + Agent            │ "这个改动改变了什么？" │
   │ 理解门槛     │ docs/understanding-gate.md │ "我懂了吗？"          │
   │ Microworld  │ microworld/               │ "我能亲手玩一遍吗？"  │
   └─────────────┴──────────────────────────┴──────────────────────┘

3. 核心原则

   > 每增加一行代码，就增加一行理解。
   > 每删除一行理解，就删除一行代码。

4. AI 协作的新范式

   旧范式: 人提需求 → AI 生成代码 → CI 通过 → 合并（没人理解）
   新范式: 人提需求 → AI 生成代码 + 知识包 + 地图更新
              → 人审查理解（不是审查代码）
              → 理解门槛通过？
                 ├─ 是 → 合并 + 更新地图
                 └─ 否 → AI 生成 Microworld → 人进去玩 → 理解 → 合并

第二部分: 场景提示词（直接复制使用）

───────────────────────────────────────────────────────────────────────────
场景 1: 写新功能 —— AI 生成代码 + 知识包
───────────────────────────────────────────────────────────────────────────

适用时机: 让 AI 帮你实现一个新功能、新模块、或修改现有代码时。

核心理念: 不要只让 AI 写代码。让它同时交付理解。

─────── 提示词模板 ───────

帮我实现以下功能：[描述你的需求]。

在写代码之前，请先阅读以下文件来理解项目上下文：
- CLAUDE.md（项目心智模型）
- docs/knowledge-map.md（系统认知地图）

在交付代码的同时，请生成一份 PR 知识包，包含以下内容：

1. 背景 (Context): 这段代码属于系统的哪个部分？在架构中的位置？

2. 问题 (Problem): 要解决什么痛点？之前为什么不行？
   - 当前痛点：
   - 期望行为：
   - 根因分析（如果已知）：

3. 心智模型 (Mental Model): 用自然语言或 ASCII 图描述核心设计思想。
   解释每一个关键设计决策的 WHY，而不只是 WHAT。

4. 数据流 (Data Flow): 用表格描述数据经过的每一步变换：
   | 阶段 | 输入 | 变换 | 输出 | 形状 |

5. 职责与边界: 这段代码负责什么？明确不负责什么？
   - 负责：
   - 不负责（边界）：
   - 不应在此改动中修改的东西：

6. 风险点: 什么情况下会出错？最可能的 bug 是什么？
   | 风险 | 触发条件 | 后果 | 缓解措施 |

7. 理解自测: 生成 3 个问题，我应该能在合并前回答出来。
   （这些问题测试理解，不测试正确性）

8. 知识地图更新: 检查 docs/knowledge-map.md 是否需要更新，
   如果需要，给出具体的修改建议（哪个章节、改什么）。

─────── 简化版（日常快速使用）───────

帮我实现 [需求]。同时生成知识包：背景、问题、
心智模型（含设计决策的 WHY）、数据流、边界和风险点。


───────────────────────────────────────────────────────────────────────────
场景 2: PR Review —— 让 AI 辅助"理解审查"
───────────────────────────────────────────────────────────────────────────

适用时机: 你在 Review 一个 PR，想确保自己不只是看了代码对不对，
         而是真正理解了改动。

核心理念: Code Review 的终点不是 "LGTM"，而是 "我懂了"。

─────── 提示词模板 ───────

我正在 Review 以下 PR 的代码改动：

[粘贴 diff 或描述改动内容]

请帮我从"理解"的角度审查这个改动，而不是从"正确性"的角度：

1. 这个改动要解决什么问题？（用一句话）

2. 帮我在脑海中跑通数据流：
   - 数据从哪里进入这个模块？
   - 经过哪些变换？
   - 最终输出了什么？
   - 有没有隐含的输入假设？

3. 这个改动的边界在哪？
   - 哪些逻辑"看起来应该在这里"但实际上在别处？
   - 哪些逻辑"看起来应该由别人处理"但实际上在这里？

4. 如果我 3 个月后要修改这段代码，最安全的切入方式是什么？

5. 生成 4 个"理解问题"，我应该能回答才能点 Approve：
   - 第1层（定位）: 这个改动在系统架构的哪个位置？
   - 第2层（数据流）: 数据经过的关键变换是什么？
   - 第3层（边界）: 这个模块不负责什么？
   - 第4层（故障）: 什么情况下这个改动会出 bug？表现是什么？

6. 检查 docs/knowledge-map.md 是否需要更新？需要的话，更新什么？

─────── 简化版 ───────

帮我审查这个改动的"可理解性"：
- 数据流是否清晰？
- 边界是否明确？
- 设计决策的 WHY 是否清楚？
- 生成 4 个我应该在 Approve 前能回答的问题。


───────────────────────────────────────────────────────────────────────────
场景 3: 新人 Onboarding —— 让 AI 生成学习路径
───────────────────────────────────────────────────────────────────────────

适用时机: 有新成员加入团队，需要快速理解系统。

核心理念: 新人不需要"读完所有文档"，需要一张地图加一个导游。

─────── 提示词模板 ───────

我是一名刚加入团队的新人。请帮我快速理解这个项目。

请先阅读以下文件来了解项目：
- CLAUDE.md
- docs/knowledge-map.md
- docs/cognitive-debt-guide.md

然后为我生成：

1. 系统概述（3 句话版本 + 3 分钟版本 + 30 分钟版本）

2. 关键概念速查表: 列出 5-10 个最重要的概念，
   每个用一句话解释，并告诉我它们在哪个文件里。

3. 学习路径（按优先级排序）:
   - 第一阶段（第1天）: 我应该先理解哪 2-3 个文件？为什么？
   - 第二阶段（第1周）: 我应该深入理解哪个子系统？
   - 第三阶段（第1月）: 我应该能独立修改哪个模块？

4. Microworld 推荐: 如果有交互式训练场（microworld/），
   推荐我按什么顺序运行哪些模块。

5. 常见陷阱: 新人最容易误解的 3 件事。

6. 知识地图导读: 帮我解读 knowledge-map.md，
   告诉我哪些区域是"安全区"（可以随意修改），
   哪些是"雷区"（需要特别小心）。

7. 理解自测: 给我 5 个问题，如果我能在第 1 周末回答出来，
   就说明我对系统有了基本的理解。


───────────────────────────────────────────────────────────────────────────
场景 4: 复杂系统 —— 让 AI 生成 Microworld
───────────────────────────────────────────────────────────────────────────

适用时机: 团队面对一个复杂的子系统（如RL训练循环、GAE计算），
         光看代码不够，需要亲手操作才能理解。

核心理念: 理解不是读出来的，是玩出来的。
         每个复杂模块都应该有一个"训练场"。

─────── 提示词模板 ───────

我想深入理解项目中的 [模块名称/子系统名称]。
相关代码在 [文件路径]。

请帮我生成一个交互式的 Microworld 脚本，设计原则如下：

1. 每次只展示一个概念
2. 每一步都解释"正在发生什么"和"为什么"
3. 所有中间值可见、可修改
4. 包含以下模块：
   a) 输入探索: 这个模块接收什么？每个输入的含义是什么？
   b) 逐步跟踪: 用假数据逐步执行，打印每一步的中间结果和解释
   c) 参数实验: 可以修改关键参数，观察输出变化
   d) 故障模拟: 模拟常见的错误输入/边界条件，观察表现
   e) 概念验证: 一个小练习，验证我真的理解了

5. 脚本应该是独立的（可直接运行），带有丰富的打印输出和注释。
   不要依赖 Jupyter Notebook——纯 .py 脚本即可。

6. 参考 microworld/ppo_playground.py 的风格和结构。

─────── 简化版 ───────

帮我为 [模块] 生成一个 Microworld 训练场脚本。
要求：逐步执行、每步解释、参数可调、独立可运行。
风格参考 microworld/ppo_playground.py。


───────────────────────────────────────────────────────────────────────────
场景 5: 知识地图维护 —— 让 AI 帮助更新认知地图
───────────────────────────────────────────────────────────────────────────

适用时机: 经过一轮开发后，系统发生了变化，需要更新知识地图。

核心理念: 谁改代码，谁更新地图。AI 改的代码，人确认，AI 更新地图。

─────── 提示词模板 ───────

我们最近做了以下改动：
[描述改动内容，或粘贴 PR 列表]

请先阅读当前的 docs/knowledge-map.md。

然后帮我更新知识地图，具体检查：

1. 模块职责矩阵: 是否有新模块需要添加？是否有模块职责发生变化？
2. 依赖图: 依赖关系是否改变？
3. 数据流: 核心数据流是否改变？
4. 雾图 (Fog Map): 哪些模块的理解度提升了？哪些需要降级？
5. 认知快照表: 哪些模块的"最后深入理解者"需要更新？
6. 关键概念速查表: 是否有新概念需要添加？

请给出具体的修改方案（要改哪个章节、怎么改），
如果需要，可以直接用 Edit 工具更新文件。

─────── 简化版 ───────

我们改了 [描述]。帮我检查 docs/knowledge-map.md 需要更新什么。


───────────────────────────────────────────────────────────────────────────
场景 6: Bug 修复 —— 不仅要修，还要"理解固化"
───────────────────────────────────────────────────────────────────────────

适用时机: 修一个 bug，特别是有深层次根因的 bug。

核心理念: 只修 bug 不改理解 = 下次还会出现。
         每个 bug 都是理解系统的机会。

─────── 提示词模板 ───────

我在项目中发现了以下 bug：
[Bug 描述 / 错误日志 / 复现步骤]

相关代码在 [文件路径]。

请帮我修复这个 bug。但我需要的不仅是修复代码，还有"理解固化"：

1. 根因分析:
   - 这个 bug 的直接原因是什么？
   - 为什么之前的测试/Lint/Review 没有发现？
   - 这个 bug 暴露了我们对系统的什么误解？

2. 修复方案（带解释）:
   - 方案 A / 方案 B（如果有多种修复方式）
   - 为什么选择这个方案？

3. 心智模型修正:
   - 这个 bug 修正了我对系统的什么理解？
   - 我之前的理解错在哪？正确的理解是什么？

4. 防范措施:
   - 如何防止同类 bug 再次出现？
   - 需要添加什么测试/断言/文档？
   - 有没有类似的代码也需要检查？

5. 知识包更新:
   - 这个 bug 的修复是否需要更新 docs/knowledge-map.md？
   - 是否需要在代码中加注释，防止未来的人踩同样的坑？
   - 生成 3 个"理解问题"，团队应该能回答以避免重蹈覆辙。

─────── 简化版 ───────

帮我修复 [bug]，同时做根因分析 + 心智模型修正 + 防范措施。
不要只给我代码，给我理解。


───────────────────────────────────────────────────────────────────────────
场景 7: 重构 —— 在改动中保持认知连续性
───────────────────────────────────────────────────────────────────────────

适用时机: 重构一个模块或子系统。

核心理念: 重构容易产生"认知断层"——新代码没人懂，旧理解全报废。
         重构时必须同步更新所有认知防御层的文档。

─────── 提示词模板 ───────

我想重构 [模块名称]，目标是 [重构目标]。
当前代码在 [文件路径]。

在进行重构之前，请先：
1. 阅读 CLAUDE.md 和 docs/knowledge-map.md
2. 分析当前模块的职责、数据流、依赖关系
3. 列出重构会影响的所有文件

然后帮我完成重构，并在重构完成后交付：

1. 重构前后的心智模型对比:
   - 用 ASCII 图画出重构前和重构后的结构
   - 标注关键变化点

2. 迁移清单:
   - 哪些概念保留但实现变了？
   - 哪些概念被废弃？
   - 哪些概念是新引入的？

3. 数据流变化:
   - 重构前后的数据流对比表

4. 知识地图更新:
   - docs/knowledge-map.md 需要修改的所有地方

5. 理解过渡指南:
   - 给已经理解旧代码的团队成员写一段"迁移笔记"
   - "你以前知道 X，现在 X 变成了 Y，原因是 Z"

6. 新理解自测:
   - 生成 5 个问题，团队在重构后应该能回答

─────── 简化版 ───────

帮我重构 [模块]。要求：重构前后心智模型对比 +
知识地图更新 + 团队理解过渡指南。


───────────────────────────────────────────────────────────────────────────
场景 8: 日常编码 —— 让 AI 帮你"出声思考"
───────────────────────────────────────────────────────────────────────────

适用时机: 在自己写代码（而非 AI 生成）时，让 AI 扮演"理解审查员"。

核心理念: AI 不一定要帮你写代码——它可以帮你审视你对代码的理解。

─────── 提示词模板 ───────

我写了以下代码：
[粘贴你的代码]

请不要帮我修改它。我只想让你帮我检验我的理解：

1. 根据代码，反推出我的设计意图。我可能想解决什么问题？
   （这能验证代码是否表达了我的意图）

2. 找出代码中可能让人困惑的地方。
   如果一个 3 个月后的同事读这段代码，他会在哪里卡住？

3. 指出隐含的假设。
   我的代码对输入数据做了什么假设？在哪一行？

4. 边界检查。
   这段代码在什么输入下会出错？

5. 生成这段代码的"3 句话解释"。
   如果我被问到"这段代码做什么"，我应该怎么回答？

─────── 简化版 ───────

帮我审查这段代码的"可理解性"：反推设计意图 +
找出困惑点 + 指出隐含假设 + 边界检查。


───────────────────────────────────────────────────────────────────────────
场景 9: 知识传递 —— 写技术文档 / 交接文档
───────────────────────────────────────────────────────────────────────────

适用时机: 需要写模块文档、交接文档、或向团队做技术分享。

核心理念: 写文档不是为了"有文档"，是为了"传递心智模型"。

─────── 提示词模板 ───────

我需要为 [模块名称]（代码在 [文件路径]）写一份技术文档，
目标是让一个没看过代码的同事在 30 分钟内建立基本的心智模型。

请先阅读相关代码和 docs/knowledge-map.md。

然后帮我生成以下内容：

1. 一句话概要: 这个模块做什么？（不超过 30 字）

2. 心智模型图: 用 ASCII 或 Mermaid 画出核心概念和数据流

3. 关键概念表:
   | 概念 | 一句话解释 | 代码位置 |

4. 数据流 Walkthrough: 用"假设我是一个数据包"的视角，
   逐步描述我经过的每一个变换。

5. 常见操作: 列出 3-5 个最常见的修改场景，
   每个场景告诉读者应该改哪个文件、哪个函数。

6. FAQ: 新人问得最多的 5 个问题 + 答案

7. 边界和陷阱: 这个模块最容易用错的 3 种方式

8. 推荐配合阅读: 要理解这个模块，最好先读哪些文件/文档？

─────── 简化版 ───────

帮我为 [模块] 写交接文档：心智模型图 + 数据流 Walkthrough
+ 常见操作 + FAQ + 陷阱。


───────────────────────────────────────────────────────────────────────────
场景 10: 团队认知 Sync —— 周会/迭代回顾
───────────────────────────────────────────────────────────────────────────

适用时机: 每周或每迭代结束时，团队一起审视认知债务的变化。

核心理念: 认知债务是渐进的。需要定期"对账"——
         代码变了多少，理解跟上了多少。

─────── 提示词模板 ───────

我们团队本周做了以下 PR：
[List of PRs or changes]

请帮我生成一份"认知 Sync"报告，用于团队周会讨论：

1. 本周变化概览:
   - 哪些模块发生了变化？
   - 新增了哪些概念？
   - 废弃了哪些概念？

2. 认知债务变化评估:
   - 雾图变化: 哪些区域变清晰了？哪些变模糊了？
   - 有没有新增的"无人区"（没人懂的模块）？
   - 有没有"单点故障"（只有一个人懂的模块）？

3. 理解债务清单:
   - 哪些模块的代码改了但文档没更新？
   - 哪些 PR 跳过了理解门槛？

4. 下周改进建议:
   - 团队下周应该优先理解什么？
   - 有没有需要生成 Microworld 的复杂模块？

5. 团队讨论问题（3 个）:
   - 例如: "模块 X 现在有 3 个版本，我们确定哪个是主版本吗？"

─────── 简化版 ───────

本周我们改了 [描述]。帮我评估认知债务变化：
清晰区域、模糊区域、单点故障、文档缺口。

以下是可以插入任何提示词的"认知防御模块"。

─── 模块 A: 强制上下文 ───

在开始之前，请先阅读以下文件：
- CLAUDE.md — 项目心智模型
- docs/knowledge-map.md — 系统认知地图
- docs/cognitive-debt-guide.md — 认知债务防御指南

─── 模块 B: 强制知识包输出 ───

无论你生成什么代码，请在代码之后附带"知识包"：
1. 这个改动在系统架构的哪个位置？
2. 数据从哪来、经过什么变换、到哪去？
3. 每个设计决策的 WHY（为什么选这个方案而不是其他方案）
4. 边界（明确不负责什么）
5. 更新 docs/knowledge-map.md 的建议

─── 模块 C: 强制理解自测 ───

在交付代码后，请生成 3 个"理解问题"。
这些问题测试的不是代码的正确性，而是读者是否真正理解了改动的意图、
数据流和边界条件。我应该能在不看代码的情况下回答这些问题。

─── 模块 D: 强制反向审视 ───

请用"3个月后的同事"的视角审视你生成的代码：
- 哪些地方会让人困惑？
- 哪些假设没有明确写出来？
- 如果只读代码（不看这个对话），他能理解设计意图吗？

─── 模块 E: 强制雾图更新 ───

请评估本次改动对团队认知地图的影响：
- 是否有新概念需要加入关键概念速查表？
- 是否有模块的理解度需要调整？
- docs/knowledge-map.md 的哪个章节需要更新？

第五部分: 给 AI 的系统指令（可放入 CLAUDE.md 或 .claude/ 配置中）
═══════════════════════════════════════════════════════════════════════════

如果你想让 AI 默认就遵循认知债务防御的原则，
可以将以下内容添加到 CLAUDE.md 或项目配置中：

─── 推荐添加到 CLAUDE.md ───

## AI 协作原则 (Cognitive Debt Defense)

当为本项目生成代码时，请遵循以下原则：

1. 每次生成代码时，附带"知识包"：
   - 背景（改动在架构中的位置）
   - 问题（为什么需要这个改动）
   - 心智模型（用自然语言或图解释设计思想，包括 WHY）
   - 数据流（输入→变换→输出）
   - 边界（明确不负责什么）
   - 风险点（最可能的故障模式）

2. 生成 3 个"理解自测"问题，测试理解而非正确性。

3. 检查 docs/knowledge-map.md 是否需要更新，给出具体建议。

4. 用"3个月后的同事"视角审视代码的可读性：
   - 去掉对话上下文后，代码本身是否自解释？
   - 关键设计决策的 WHY 是否体现在代码注释中？

5. 对于复杂逻辑（>20行或涉及多个文件交互），
   建议在 microworld/ 中生成对应的训练场脚本。

6. 永远不要只交付代码。交付代码 + 理解。

本手册对应的工具文件:

  CLAUDE.md                          — AI 项目心智模型（每次对话自动加载）
  docs/knowledge-map.md              — 团队认知地图（Mermaid图 + 雾图 + 职责矩阵）
  docs/understanding-gate.md         — 理解门槛（四层理解审查清单）
  docs/cognitive-debt-guide.md       — 认知债务防御实践指南（本文档的理念篇）
  .github/pull_request_template.md   — PR 知识包模板
  microworld/ppo_playground.py       — PPO 交互式训练场（示例 Microworld）
  .claude/agents/knowledge-pack-generator.md — AI Agent: 自动生成 PR 知识包

工具之间的配合关系:

  写代码时:
    CLAUDE.md (上下文) → 场景1提示词 (生成代码+知识包)
    → PR模板 (格式化) → Knowledge Pack Generator Agent (自动化)

  Review 时:
    场景2提示词 (理解审查) → Understanding Gate (四层检查)
    → Knowledge Map (定位改动) → Approve/Reject

  维护时:
    场景5提示词 (地图更新) → Knowledge Map (保持最新)
    场景10提示词 (认知Sync) → 团队周会讨论

  深度理解时:
    场景4提示词 (生成Microworld) → microworld/ (交互探索)
    → Understanding Gate (验证理解)
